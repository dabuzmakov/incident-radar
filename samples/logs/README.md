# Сэмплы логов

Готовые NGINX-логи для разработки и тестов. Составлять их самому не нужно —
это не учебная цель.

Файлы сгенерированы детерминированно, поэтому статистика по ним всегда одна
и та же, и ей можно сверять свою реализацию.

## Файлы

| Файл | Строк | Зачем |
|---|---|---|
| `access-2025-03-01.log` | 1500 | Основной набор, первый день |
| `access-2025-03-02.log` | 1500 | Второй день — нужен для glob-маски и фильтра по датам |
| `reference-codes.log` | 6 | Эталон для теста распределения кодов ответа |
| `reference-sizes.log` | 5 | Эталон для теста статистики размеров |
| `malformed.log` | 13 | Корректные и битые строки вперемешку; пригодных записей — 7 |

## Как запускать

```bash
# Один файл
dotnet run --project src/IncidentRadar.App -- --path samples/logs/access-2025-03-01.log --output-format markdown --output-path report.md

# Оба файла по glob-маске (кавычки обязательны, иначе маску раскроет shell)
dotnet run --project src/IncidentRadar.App -- --path 'samples/logs/access-*.log' --output-format json --output-path report.json

# С фильтром по датам
dotnet run --project src/IncidentRadar.App -- --path 'samples/logs/access-*.log' --from 2025-03-02 --output-format markdown --output-path day2.md
```

ровно по этой причине.

## Эталонные файлы

### `reference-codes.log`

Шесть запросов со статусами `200, 200, 404, 500, 500, 500`.

Ожидаемое распределение: `200 -> 2`, `404 -> 1`, `500 -> 3`.

### `reference-sizes.log`

Пять запросов с размерами ответа `100, 200, 300, 400, 500`.

Ожидается: `average = 300`, `max = 500`. При любом разумном методе
расчёта `p95 = 500`.

### `malformed.log`

13 строк, и поломки в них **двух разных видов** — это сделано намеренно.

**Пять строк не подходят под формат вообще.** Их отбракует любая проверка
структуры:

| Строка | Что не так |
|---|---|
| `` (пустая) | Пустая строка |
| `это вообще не лог` | Произвольный текст |
| `93.180.71.3 - - [...] "GET /downloads/product_1 HTTP/1.1"` | Обрезана: нет статуса, размера и кавычек |
| `... "GET /api/v1/cards HTTP/1.1" двести 512 ...` | Статус не число |
| `- - - [...] "" 200 0 "-" "-"` | Пустой `$request` |

**Одна строка формату соответствует, но всё равно битая:**

```text
93.180.71.3 - - [НЕ-ДАТА] "GET /api/v1/cards HTTP/1.1" 200 512 "-" "curl/8.7.1"
```

Регулярка вида `\[([^\]]+)\]` такую строку спокойно пропустит — поле на месте,
скобки на месте. Упадёт уже разбор даты, и если этот вызов не обёрнут в
обработку ошибки, программа завершится с исключением на середине гигабайтного
файла.

Именно поэтому «проверить формат регуляркой» и «разобрать значения» — два
разных шага, и упасть можно на любом из них.

**Итого: корректно разобранных записей должно быть 7.**

Правильное поведение: битые строки **пропускаются** с записью
`WARN: skipped malformed log line`, программа не падает. Битая строка —
ожидаемый сценарий, а не повод завершиться с ошибкой: в логе с реального
прода мусор есть всегда.
